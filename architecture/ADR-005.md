# 📄 ADR-005

## MVP-Strategie zur Integration externer SVWS-Server (Synchronisation & Resilienz)

---

**Status:** Accepted (MVP)
**Datum:** 2026-02-14
**Autor:** Architekturteam Schulträger-Server
**Referenzen:**

* ADR-001 (Hexagonale Architektur)
* ADR-003 (Authentifizierung & JWT)
* ADR-004 (Multi-Tenancy-Strategie)
* arc42 Abschnitt 6 (Laufzeitsicht)
* arc42 Abschnitt 8 (Querschnittliche Konzepte – Fehlerbehandlung)

---

# 1. Kontext

Der Schulträger-Server soll im MVP:

* Schulen eines Mandanten verwalten
* Verbindung zu externen SVWS-Servern herstellen
* Privileged-API auf SVWS nutzen
* Status der Verbindung anzeigen
* Synchronisationsstatus speichern
* ausschließlich mit Rolle `ADMIN` betrieben werden

Rahmenbedingungen:

* Externe SVWS-Server sind nicht unter unserer Kontrolle
* Netzwerkfehler sind realistisch
* SVWS kann nicht erreichbar sein
* Keine Event-Architektur im MVP
* Keine asynchrone Queue im MVP

---

# 2. Ziel des MVP

Das System soll ermöglichen:

* Schule anlegen (inkl. SVWS-URL + Zugangsdaten)
* Verbindungsprüfung durchführen
* Schul-Information vom SVWS abrufen
* Synchronisationsstatus speichern
* Fehler transparent anzeigen

Keine automatische Hintergrund-Synchronisation im MVP.

---

# 3. Entscheidung

Die SVWS-Integration im MVP wird umgesetzt als:

> Synchrone REST-Kommunikation mit kontrollierter Fehlerbehandlung
> ohne Messaging-System und ohne Circuit Breaker Infrastruktur

# 5. Integrationsstrategie

## 5.1 Kommunikationsart

* REST over HTTPS
* Quarkus REST Client
* Synchrone Aufrufe
* Timeout konfiguriert

---

## 5.2 Use Cases im MVP

### 1. Schule anlegen

Speichern von:

* Name
* SVWS-URL
* API-Credentials
* Status = `UNVERIFIED`

---

### 2. Verbindung testen

Backend ruft auf:

```
GET /api/privileged/user/isprivileged
```

Erwartet: `true`

Ergebnis:

| Fall             | Status              |
| ---------------- | ------------------- |
| Erfolgreich      | VERIFIED            |
| Nicht privileged | INVALID_CREDENTIALS |
| Timeout          | UNREACHABLE         |
| 500              | ERROR               |

---

### 3. Schulinfos synchronisieren

Aufruf:

```
GET /api/schema/liste/info/{schema}/schule
```

Speichern:

* Schulname
* Schulnummer
* Letztes Sync-Datum
* Sync-Status

---

# 6. Fehlerstrategie (MVP-Level)

Keine Circuit-Breaker-Infrastruktur.

Stattdessen:

## 6.1 Technische Maßnahmen

* Connect Timeout (z. B. 5s)
* Read Timeout (z. B. 10s)
* Fehler werden gefangen und klassifiziert
* Keine Retry-Mechanik im MVP

---

## 6.2 Fehlerklassifikation

| Fehler         | Behandlung           |
| -------------- | -------------------- |
| Timeout        | Status = UNREACHABLE |
| 401/403        | INVALID_CREDENTIALS  |
| 500            | ERROR                |
| JSON Fehler    | ERROR                |
| Netzwerkfehler | UNREACHABLE          |

Fehler werden gespeichert in:

```sql
last_error TEXT
last_sync_status VARCHAR
last_sync_at TIMESTAMP
```

---

# 7. Resilienz-Entscheidung (bewusst MVP)

Nicht implementiert:

* ❌ Circuit Breaker
* ❌ Retry mit Backoff
* ❌ Asynchrone Verarbeitung
* ❌ Message Queue
* ❌ Event Streaming
* ❌ Bulk Synchronisation

Begründung:

* Komplexität zu hoch für MVP
* Nur manuelle Admin-Aktionen
* Geringe Last
* Fokus auf Kernfunktion

---

# 8. Rollenmodell im MVP

Nur eine Rolle:

```
ADMIN
```

Darf:

* Schulen anlegen
* Schulen bearbeiten
* Verbindung testen
* Synchronisieren
* Status einsehen

Noch nicht vorhanden:

* Verwaltungsmitarbeiter
* Leserechte
* Modulbasierte Rechte

Architektur bleibt aber erweiterbar (siehe ADR-003).

---

# 9. Logging-Strategie (MVP)

Bei jedem SVWS-Aufruf:

* Log Request-ID
* Log Schule-ID
* Log Dauer
* Log Status

Kein zentrales Monitoring-System im MVP.

---

# 10. Persistenzmodell (MVP)

Tabelle `schule` enthält zusätzlich:

```sql
svws_url VARCHAR
svws_username VARCHAR
svws_password VARCHAR (verschlüsselt gespeichert)
last_sync_at TIMESTAMP
last_sync_status VARCHAR
last_error TEXT
```

Passwort wird:

* verschlüsselt gespeichert
* niemals im Log ausgegeben

---

# 11. Sicherheitsmaßnahmen

* HTTPS verpflichtend
* Credentials verschlüsselt
* Zugriff nur für ADMIN
* Keine SVWS-Credentials im Frontend

---

# 12. Konsequenzen

## Positive

* Schnell implementierbar
* Einfach verständlich
* Geringe Komplexität
* Klare Statusanzeige
* Stabiler MVP

## Negative

* Keine automatische Resilienz
* Keine Skalierung bei vielen Schulen
* Keine Retry-Strategie
* Manuelle Bedienung notwendig

---

# 13. Erweiterungspfad (V2)

Später möglich:

* Retry mit Exponential Backoff
* Circuit Breaker (SmallRye Fault Tolerance)
* Async Worker
* Scheduled Sync
* Bulk Sync
* Event-driven Integration
* Monitoring & Metrics

# 15. Gültigkeit

Diese Integrationsstrategie gilt für:

* MVP Phase
* Rolle ADMIN
* Schulverwaltung
* Manuelle Synchronisation

Eine Erweiterung auf produktionskritische Resilienz erfordert ein neues ADR.
