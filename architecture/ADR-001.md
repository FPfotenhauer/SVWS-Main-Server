# 📄 ADR-001

## Einführung einer hexagonalen Architektur mit Quarkus als Backend-Framework

---

**Status:** Accepted
**Datum:** 2026-02-12
**Autor:** Architekturteam Schulträger-Server
**Referenzen:** arc42 Abschnitt 4 (Lösungsstrategie), Abschnitt 5 (Bausteinsicht)

---

# 1. Kontext

Der Schulträger-Server soll:

* viele Schulen verwalten
* mit mehreren externen SVWS-Server-Instanzen kommunizieren
* langfristig erweiterbar sein (Multi-Tenancy, Monitoring, Async Sync)
* wartbar über viele Jahre betrieben werden
* sicher und robust gegenüber externen Systemfehlern sein

Das System wird schrittweise wachsen:

* MVP: Schulverwaltung + SVWS Sync
* V2: Mandantenfähigkeit
* V3: Event-basierte Synchronisation
* V4: Zentrale Benutzerverwaltung

Daher ist eine saubere Architekturentscheidung zu Beginn entscheidend.

---

# 2. Problemstellung

Ohne klare Architektur besteht das Risiko von:

* starker Kopplung an SVWS
* Logik in Controllern
* schwer testbarer Business-Logik
* späteren Refactoring-Kosten
* mangelnder Erweiterbarkeit

Es muss entschieden werden:

> Welche Architekturstruktur wird für das Backend gewählt?

---

# 3. Entscheidung

Der Schulträger-Server wird im Backend nach folgenden Prinzipien aufgebaut:

## ✅ Hexagonale Architektur (Ports & Adapters)

Struktur:

* **Domain Layer**
  Enthält reine Geschäftslogik ohne Framework-Abhängigkeiten.

* **Application Layer**
  Enthält Use Cases und orchestriert Domain + Ports.

* **Infrastructure Layer**
  Implementiert:

  * Datenbankzugriff (Hibernate Panache)
  * REST Clients (SVWS)
  * Security (JWT)
  * externe Systeme

* **API Layer**
  REST-Endpunkte (JAX-RS)

---

## ✅ Quarkus als Backend-Framework

Begründung:

* Cloud-native Architektur
* Sehr schnelle Startup-Zeit
* Gute Integration mit:

  * Hibernate
  * REST Client
  * Security (JWT)
  * Docker
* Gute Eignung für Microservices (Zukunftsfähigkeit)

---

## ✅ Ports & Adapter Prinzip

Beispiel:

```
Application Layer
     |
     |  (Port)
     v
SvwsClient (Interface)
     |
     |  (Adapter)
     v
SvwsClientRest (Quarkus REST Client)
```

Dadurch:

* Mocking möglich
* Austauschbarkeit möglich
* Testbarkeit hoch
* klare Trennung externer Systeme

---

# 4. Konsequenzen

## Positive Konsequenzen

* Hohe Wartbarkeit
* Testbarkeit ohne Infrastruktur
* Geringe Kopplung an SVWS
* Vorbereitung für Multi-Tenancy
* Vorbereitung für Event-Architektur
* Vorbereitung für Microservices

## Negative Konsequenzen

* Höherer Initialaufwand
* Mehr Klassen
* Strengere Strukturdisziplin notwendig

---

# 5. Abgelehnte Alternativen

## ❌ Monolith ohne Layer-Trennung

Problem:

* Business-Logik in Controllern
* schwer testbar
* spätere Umstrukturierung teuer

---

## ❌ Reine CRUD-Architektur mit direkter DB + REST Client Nutzung

Problem:

* keine saubere Trennung
* hohe Kopplung
* fehlende Austauschbarkeit externer Systeme

---

## ❌ Spring Boot statt Quarkus

Begründung der Ablehnung:

* Höherer Ressourcenverbrauch
* Kein nativer Fokus auf Cloud/Container-Optimierung
* Quarkus passt besser zur Zielarchitektur

---

# 6. Auswirkungen auf Projektstruktur

Verzeichnisstruktur:

```
backend/src/main/java/de/schultraeger/

  domain/
  application/
  infrastructure/
  api/
```

Regel:

* Domain kennt nichts aus Infrastructure
* Application kennt nur Ports
* Infrastructure implementiert Ports
* API ruft Application auf
