# 📄 ADR-004

## Multi-Tenancy-Strategie für den Schulträger-Server

---

**Status:** Accepted
**Datum:** 2026-02-14
**Autor:** Architekturteam Schulträger-Server
**Referenzen:**

* ADR-001 (Hexagonale Architektur)
* ADR-002 (Persistenzstrategie)
* arc42 Abschnitt 4 (Lösungsstrategie)
* arc42 Abschnitt 8 (Querschnittliche Konzepte)

---

# 1. Kontext

Der Schulträger-Server verwaltet:

* Einen oder mehrere Schulträger (Über eigene Instanzen pro Träger)
* Viele Schulen je Schulträger
* Externe SVWS-Server je Schule
* Zukünftig Benutzer, Rollen, Rechte, Logs

Langfristige Anforderungen:

* Möglichkeit, mehrere Schulträger zu betreiben
* Strikte Datenisolation zwischen Mandanten
* Mandantenfähige Rollenmodelle
* Vorbereitung für SaaS-Betrieb
* Erweiterbarkeit ohne Re-Architektur

Es muss entschieden werden:

> Wie wird Mandantenfähigkeit umgesetzt?

---

# 2. Begriffsklärung

**Mandant (Tenant)** = Schulträger

Begründung:

* Schulträger ist die organisatorische Einheit
* Schulen gehören logisch zu einem Schulträger
* Schulträger sind voneinander isoliert
* Deployment kann später SaaS-fähig sein

Schule ist **keine** Mandanteneinheit, sondern eine Domänen-Entität.

---

# 3. Betrachtete Alternativen

## Option A – Separate Datenbank pro Mandant

**Vorteile**

* Maximale Isolation
* Einfache rechtliche Trennung

**Nachteile**

* Hoher Betriebsaufwand
* Migrationen mehrfach
* Monitoring komplex
* Skalierung ineffizient
* Deployment-Overhead

Wird langfristig umgesetzt.
✅ **Diese Option wird gewählt.**

---

## Option B – Schema pro Mandant (PostgreSQL Schema)

**Vorteile**

* Gute Isolation
* Gemeinsame Infrastruktur
* Gute Strukturierung

**Nachteile**

* Komplexe Migrationen
* Flyway schwieriger
* Querying über Mandanten hinweg komplex
* Dev/Test Setup kompliziert

Abgelehnt für V1.

---

## Option C – Gemeinsame Datenbank, Mandanten-ID pro Tabelle

Struktur:

```sql
tenant_id UUID NOT NULL
```

**Vorteile**

* Einfacher Betrieb
* Einfache Migration
* Saubere Erweiterbarkeit
* Gute Performance
* Gut mit Flyway kombinierbar
* SaaS-geeignet
* Gute Integration mit Quarkus

**Nachteile**

* Strikte Disziplin notwendig
* Fehlerhafte Queries können Isolation brechen

Abgelehnt da ein Container pro Schulträger gut umsetzbar ist.

---

# 4. Entscheidung

Der Schulträger-Server verwendet:

> Separate Datenbanken pro Mandant (DB-per-tenant)

---

# 6. Isolationsebene

Isolation erfolgt auf:

| Ebene       | Umsetzung                                                   |
| ----------- | ----------------------------------------------------------- |
| API         | Security Filter prüft User                                   |
| Application | Mandantenzuordnung erfolgt über Deployment / DB-Verbindung  |
| Index       | Performance-Sicherung                                        |

---

# 7. Sicherheitsmodell (Vorbereitung für ADR-003)

JWT enthält:

```json
{
  "sub": "user-id",
  "roles": ["ADMIN"]
}
```

Security Context stellt Identität und Rollen bereit. Die Mandanten-Auflösung erfolgt nicht aus dem JWT, sondern über die Deployment- / Verbindungs-Konfiguration, welche die richtige Datenbank für den Mandanten auswählt.


---

# 8. Konsequenzen

Die gewählte DB-per-tenant-Strategie hat weitreichende Auswirkungen auf Betrieb, Entwicklung und Organisation. Im Folgenden sind die wichtigsten Konsequenzen zusammengefasst.

## Positive

* Maximale Datenisolation: Physische Trennung reduziert das Risiko von Cross-Tenant-Datenlecks.
* Rechtliche und operative Trennung: Mandantenspezifische Backups/Restores und Datenaufbewahrung sind einfacher umsetzbar.
* Einfache Anwendungsschicht: Keine generische `tenant_id`-Spalte nötig; Business-Logik muss nicht tenant-filternd sein.
* Unabhängige Skalierung: Mandanten können durch eigene DB-Ressourcen separat skaliert werden.

## Negative

* Höherer operativer Aufwand: Provisionierung, Migrationsausführung, Backups und Monitoring müssen für viele Datenbanken verwaltet werden.
* Migrationskomplexität: Flyway-Migrationen müssen orchestriert und auf allen Mandanten konsistent angewendet werden.
* Ressourcen- und Kostenanstieg: Mehr DB-Instanzen / Connections erzeugen zusätzlichen Ressourcenbedarf.
* Kompliziertere Querschnitts-Analysen: Mandantenübergreifendes Reporting erfordert ETL oder ein zentrales Data-Warehouse.
* Fehleranfälligkeit bei Konfiguration: Falsche DB-Zuordnungen (DB-URL/Credentials) können zu Datensichtbarkeitsproblemen führen.

---

# 9. Qualitätsziele (konkretisiert für DB-per-tenant)

| Ziel                 | Bewertung / Maßnahme |
| -------------------- | -------------------- |
| Isolation            | Sehr hoch (physische Trennung) |
| Wartbarkeit          | Mittel bis Hoch (Automatisierung erforderlich) |
| Skalierbarkeit       | Hoch (per-tenant Skalierung möglich) |
| Performance          | Hoch (isolierte DBs optimierbar) |
| Sicherheit           | Sehr hoch (DB-Level-Segmentierung) |
| Betriebsaufwand      | Mittel (Automatisierung reduziert Aufwand) |
| Erweiterbarkeit      | Hoch (Mandanten unabhängig erweiterbar) |

---

# 10. Betriebsmodell

* Provisionierung: Mandanten werden durch einen automatisierten Provisionierungs-Workflow (Infrastructure-as-Code oder DB-Operator) angelegt, inklusive DB, Benutzer und Rollen.
* Migrationen: CI/CD-Pipeline führt Flyway-Migrationen orchestriert und idempotent für alle Mandanten-Datenbanken aus; Preflight-Checks prüfen Kompatibilität.
* Backup & Restore: Mandantenspezifische Backups und Test-Restore-Prozesse sind Teil des Betriebs (Playbooks vorhanden).
* Monitoring & Alerting: Pro-Mandant-Metriken werden gesammelt; aggregierte Dashboards und mandantenspezifische Alerts sind verfügbar.
* Konfiguration: Backend-Deployments / Connection-Pools erhalten mandantenspezifische DB-URLs/Credentials (z. B. via Secrets-Manager oder Env-Konfiguration).

---

# 11. Risiken und Gegenmaßnahmen

| Risiko                                              | Gegenmaßnahme |
| --------------------------------------------------- | ------------- |
| Falsche DB-Zuordnung (falsche DB-URL)               | Automatisierte Validierung, End-to-End Tests, Canary-Rollouts |
| Unterschiedliche Migrationsstände                     | Orchestriertes Migrations-Management, Preflight-Checks, Idempotente Skripte |
| Operativer Overhead (Backups, Updates)               | Automatisierung / Operator, Self-Service-Tools |
| Ressourcenprobleme bei hoher Mandantenanzahl         | Monitoring, Quotas, Sharding-Strategien |
| Schwierige mandantenübergreifende Analysen           | Zentrales Reporting / Data-Warehouse, dedizierte Exportprozesse |

---

# 12. Zukunftserweiterungen

Empfohlene Erweiterungen zur Reduktion von Aufwand und Risiko:

* DB-Operator / Infrastructure-as-Code zur automatischen Mandanten-Provisionierung und Lifecycle-Management
* Orchestriertes Migrations-Tooling (Rollout + Rollback + Reporting)
* Zentralisiertes Metrics- und Logging-Frontend mit Mandanten-Kennzeichnung
* Quota- und Billing-Mechanik bei SaaS-Betrieb
* Automatisierte Test-Restores zur Sicherstellung von Recovery-Prozessen

---

# 13. Gültigkeit

Diese Multi-Tenancy-Strategie gilt für:

* Alle Anwendungsdaten (werden mandantenspezifisch in separaten DBs gehalten)
* Alle neuen Module, sofern nicht explizit ein anderes ADR vorgeschrieben ist

Abweichungen müssen durch ein separates ADR dokumentiert werden.

---

# 🔥 Strategischer Effekt

Mit dieser Entscheidung:

* Erhöht sich die Datensicherheit und rechtliche Trennbarkeit deutlich (mandantenspezifische Backups/Restores möglich).
* Steigen Betriebs- und Automatisierungsanforderungen; Investition in Operator- und CI/CD-Tooling ist nötig.
* Vereinfachen sich Teile der Anwendungsentwicklung (keine `tenant_id`-Filter), während Infrastruktur- und Release-Engineering komplexer werden.
* Bleibt ADR-003 (Security) klar getrennt: JWT beschreibt Identität/Rollen, Mandantenauflösung erfolgt über Deployment/DB-Konfiguration.
