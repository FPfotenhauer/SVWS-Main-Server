# 📄 ADR-003

## Authentifizierungs- und Autorisierungsstrategie (JWT-basiert mit OpenID Connect)

---

**Status:** Accepted
**Datum:** 2026-02-14
**Autor:** Architekturteam Schulträger-Server
**Referenzen:**

* ADR-001 (Hexagonale Architektur)
* ADR-002 (Persistenzstrategie)
* ADR-004 (Multi-Tenancy-Strategie)
* arc42 Abschnitt 8 (Querschnittliche Konzepte – Sicherheit)

---

# 1. Kontext

Der Schulträger-Server:

* Ist mandantenfähig (Tenant = Schulträger)
* Verwaltet sensible Schuldaten
* Kommuniziert mit externen SVWS-Systemen
* Wird perspektivisch SaaS-fähig betrieben
* Benötigt rollenbasierte Zugriffskontrolle

Anforderungen:

* Sichere Authentifizierung
* Mandanten-Isolation
* Rollen- und Rechte-Modell
* Erweiterbarkeit für SSO
* Unterstützung für Service-Accounts
* Stateless Backend (Cloud-ready)

Es muss entschieden werden:

> Wie wird Authentifizierung und Autorisierung umgesetzt?

---

# 2. Entscheidung

Der Schulträger-Server verwendet:

> JWT-basierte Authentifizierung über OpenID Connect
> mit einem externen Identity Provider (IdP), bevorzugt Keycloak.

---

# 3. Architekturüberblick

```text
User → Browser → Vue SPA → Backend (Quarkus)
                      ↓
                 Identity Provider (OIDC)
```

* Login erfolgt beim Identity Provider
* Backend validiert JWT
* Backend bleibt stateless

---

# 4. Identitätsprovider

## Gewählt: Keycloak (oder OIDC-kompatibler IdP)

Begründung:

* Open Source
* Mandantenfähig (Realm-Struktur)
* Rollen- und Gruppenmodell
* Gute Quarkus-Integration
* SSO-fähig
* Zukunftssicher

Alternativ möglich:

* Azure AD
* Auth0
* Schulträger-eigener OIDC Provider

System bleibt OIDC-konform.

---

# 5. Token-Strategie

## Access Token: JWT

Signiert vom IdP.

Enthält:

```json
{
  "sub": "user-id",
  "preferred_username": "admin",
  "roles": ["TENANT_ADMIN"],
  "iat": 1710000000,
  "exp": 1710003600
}
```

---

## Pflicht-Claims

| Claim     | Bedeutung             |
| --------- | --------------------- |
| sub       | User-ID               |
| roles     | Rollen                |
| exp       | Ablaufzeit            |

---

# 6. Mandantenintegration (Bezug zu ADR-004)

Mandanten werden durch separate Datenbanken pro Mandant isoliert (siehe ADR-004). Das Backend erwartet, dass die jeweilige Datenbankverbindung bereits den richtigen Mandanten kontextiert (z. B. über unterschiedliche Deployments, DB-URLs oder Connection-Pools pro Mandant).

Wesentliche Punkte:

- Der JWT enthält kein `tenant_id`-Claim mehr.
- Die Mandantenzuordnung erfolgt nicht aus dem JWT, Request-Headern oder Request-Body.
- SecurityContext stellt wie bisher Identität und Rollen bereit; die Mandantenauflösung erfolgt außerhalb des Anwendungsdatenmodells.

Application Layer muss weiterhin rollenbasierte Autorisierung prüfen, die Mandanten-Isolation wird jedoch durch die separate Datenbankinstanz sichergestellt.

---

# 7. Autorisierungsmodell

## Rollenbasiert (RBAC)

Beispielrollen:

| Rolle           | Beschreibung                  |
| --------------- | ----------------------------- |
| TENANT_ADMIN    | Vollzugriff innerhalb Mandant |
| TENANT_SUPPORT  | Support innerhalb Mandant     |
| TENANT_READONLY | Nur Lesezugriff               |
| PLATFORM_ADMIN  | Mandantenübergreifend         |

---

## Rollenprüfung

In Quarkus:

```java
@RolesAllowed("TENANT_ADMIN")
```

Zusätzlich:

* Tenant-Prüfung im Application Layer

---

# 8. Backend-Sicherheitsarchitektur

## Quarkus OIDC Extension

Verwendet:

```
quarkus-oidc
quarkus-smallrye-jwt
```

Features:

* Automatische JWT-Validierung
* Signaturprüfung
* Ablaufprüfung
* Claim-Mapping

Backend ist vollständig stateless.

---

# 9. Service-to-Service Kommunikation

Für interne Kommunikation (z. B. später Microservices):

* Client Credentials Flow
* Technischer Service-Account
* Eigene Rolle: SYSTEM_SERVICE

---

# 10. Frontend-Integration (Vue)

Flow:

1. Redirect zum IdP
2. Login
3. Erhalt Access Token
4. Speicherung im Memory (nicht LocalStorage)
5. Übergabe als:

```
Authorization: Bearer <token>
```

Kein Session-State im Backend.

---

# 11. Token-Flow

## Authorization Code Flow mit PKCE

Begründung:

* Sicher für SPA
* Industriestandard
* Schutz vor Token-Leak

---

# 12. Sicherheitsprinzipien

| Prinzip               | Umsetzung               |
| --------------------- | ----------------------- |
| Zero Trust            | Jeder Request validiert |
| Least Privilege       | Rollen minimal          |
| Stateless             | Keine Server-Sessions   |
| Externalized Identity | IdP                     |

---

# 13. Abgelehnte Alternativen

## ❌ Eigene Login-Implementierung

Problem:

* Sicherheitsrisiko
* Hoher Wartungsaufwand
* Keine SSO-Fähigkeit

---

## ❌ Session-basierte Authentifizierung

Problem:

* Nicht cloudfähig
* Skalierung schwierig
* Sticky Sessions notwendig

---

## ❌ Basic Auth

Problem:

* Unsicher
* Keine Rollen
* Keine Mandantenfähigkeit

---

# 14. Konsequenzen

## Positive

* SaaS-ready
* Skalierbar
* Mandantenfähig
* Erweiterbar
* Industriestandard
* SSO-fähig
* Kein Passwort-Handling im Backend

## Negative

* Externe Abhängigkeit (IdP)
* Initiale Konfiguration komplexer
* Token-Handling im Frontend notwendig

# 16. Betriebsmodell

Deployment:

* Keycloak als separater Container
* HTTPS verpflichtend
* TLS-Termination über Reverse Proxy
* Token-Lebensdauer konfigurierbar

Monitoring:

* Login-Events
* Fehlgeschlagene Logins
* Token-Ablaufmetriken

---

# 17. Gültigkeit

Diese Authentifizierungsstrategie gilt für:

* Alle Benutzerzugriffe
* Alle APIs
* Alle zukünftigen Module

Abweichungen nur mit eigenem ADR.
