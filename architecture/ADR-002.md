Sehr gut – Persistenz ist eine der strategisch wichtigsten Entscheidungen.
Gerade bei einem System mit externen Abhängigkeiten (SVWS), späterer Mandantenfähigkeit und möglichen Migrationen muss sie sauber festgelegt werden.

# 📄 ADR-002

## Persistenzstrategie mit PostgreSQL, Hibernate Panache und Flyway

---

**Status:** Accepted
**Datum:** 2026-02-12
**Autor:** Architekturteam Schulträger-Server
**Referenzen:**

* ADR-001 (Hexagonale Architektur)

---

# 1. Kontext

Der Schulträger-Server speichert:

* Schulträger-Stammdaten
* Schulen mit SVWS-Verbindungsdaten
* Synchronisationsstatus
* Zeitstempel und Audit-Daten
* (zukünftig) Benutzer, Rollen, Mandanten, Logs

Anforderungen an die Persistenz:

* Stabiler Betrieb im öffentlichen Umfeld
* Hohe Datenintegrität
* Transaktionssicherheit
* Migrationsfähigkeit bei Versionserweiterungen
* Vorbereitung für Multi-Tenancy
* Docker-/Cloud-Betrieb
* Klare Trennung von Domain und Infrastruktur

Es muss entschieden werden:

> Welche Datenbank, welches ORM und welche Migrationsstrategie werden verwendet?

---

# 2. Entscheidung

## ✅ Datenbank: PostgreSQL

Das System verwendet PostgreSQL als relationale Datenbank.

### Begründung:

* Open Source
* Sehr stabil und bewährt
* ACID-konform
* Sehr gute Docker-Unterstützung
* Gute Unterstützung durch Quarkus
* JSONB-Unterstützung für zukünftige flexible Strukturen
* Geeignet für Multi-Tenant-Strategien

---

## ✅ ORM: Hibernate mit Panache (Quarkus)

Es wird Hibernate ORM mit Panache verwendet.

### Begründung:

* Native Quarkus-Integration
* Reduzierter Boilerplate-Code
* Aktive Record Pattern oder Repository Pattern möglich
* Gute Testbarkeit
* Standard JPA-Unterstützung
* Zukunftssicher

---

## ✅ Migrationsstrategie: Flyway

Datenbankschemata werden ausschließlich über versionierte Migrationen mit Flyway verwaltet.

### Regeln:

* Keine automatische Schema-Generierung im Produktivbetrieb
* `quarkus.hibernate-orm.database.generation=none`
* Migrationen liegen unter:

```
backend/src/main/resources/db/migration
```

Dateiformat:

```
V1__initial_schema.sql
V2__add_status_column.sql
V3__add_audit_fields.sql
```

# 3. Architektur-Einbindung

## Schichtenbezug (aus ADR-001)

Domain Layer:

* Enthält keine JPA Annotationen

Infrastructure Layer:

* Enthält Entities
* Enthält Repository-Implementierungen

Application Layer:

* Verwendet Repository-Interfaces

Beispiel:

```
application/
   SchuleRepository (Interface)

infrastructure/
   SchuleEntity
   SchuleRepositoryPanache
```

---

# 4. Persistenzmuster

## Repository Pattern

Application kennt nur:

```java
public interface SchuleRepository {
    List<Schule> findAll();
    Optional<Schule> findById(UUID id);
    void save(Schule schule);
}
```

Infrastructure implementiert:

```java
@ApplicationScoped
public class SchuleRepositoryPanache implements SchuleRepository {
}
```

---

# 5. Transaktionsstrategie

* Transaktionen werden im Application Layer definiert
* Verwendung von `@Transactional`
* Keine Transaktionen im Controller
* Keine Transaktionen im Domain Layer

---

# 6. Audit-Strategie

Jede persistente Entity enthält:

```java
createdAt: Instant
updatedAt: Instant
```

Optional später:

* createdBy
* updatedBy

Vorbereitung für:

* vollständige Nachvollziehbarkeit
* DSGVO-Anforderungen
* Betriebsprüfungen

---

# 7. Multi-Tenancy-Vorbereitung

Die Persistenzstrategie ist kompatibel mit mehreren Multi-Tenant-Ansätzen. Für dieses Projekt gilt:

### Gewählte Strategie – Separate Datenbanken pro Mandant

Jeder Mandant betreibt eine strikt getrennte Datenbankinstanz (oder dedizierte Datenbank im selben DB-Server). Es gibt keine gemeinsame Mandanten-Spalte in den Produktivtabellen.

Vorteile:

- Volle Isolation auf Datenbankebene
- Einfachere Backups und Wiederherstellung pro Mandant
- Keine Notwendigkeit, jede Abfrage mandantenfilternd zu gestalten

Konsequenz:

* Keine `tenant_id`-Spalte in den Anwendungs-Tabellen. Migrationen und Entities sind tenant-neutral; die Mandanten-Zuordnung erfolgt durch die Deployment- / Verbindungs-Konfiguration (DB-URL, Credentials, etc.).

# 8. Abgelehnte Alternativen

## ❌ MySQL / MariaDB

* Weniger starke JSON-Funktionalität
* Geringere Konsistenzgarantien in bestimmten Konfigurationen
* PostgreSQL gilt als robuster für komplexe Systeme

---

## ❌ NoSQL (MongoDB)

Abgelehnt wegen:

* Starke relationale Datenstruktur
* Konsistenzanforderungen
* Transaktionssicherheit
* Migrationskontrolle

---

## ❌ Hibernate Auto-DDL

Abgelehnt wegen:

* Unkontrollierte Schemaänderungen
* Kein reproduzierbares Deployment
* Keine saubere Versionshistorie

---

# 9. Konsequenzen

## Positive Konsequenzen

* Vollständige Kontrolle über Schema
* Reproduzierbare Deployments
* Hohe Stabilität
* Gute Cloud-/Docker-Fähigkeit
* Gute Erweiterbarkeit
* Saubere Trennung der Schichten

## Negative Konsequenzen

* Höherer Initialaufwand
* Manuelle SQL-Migrationen notwendig
* Strikte Disziplin erforderlich

# 11. Betriebsmodell

Deployment:

* Docker Container für PostgreSQL
* Persistentes Volume
* Migration automatisch beim Start durch Flyway

Backup-Strategie (zukünftig):

* Nightly Dump
* Optional WAL-Archiving

# 12. Gültigkeit

* Alle produktiven Daten
* Alle zukünftigen Module
* Alle Erweiterungen

Abweichungen müssen durch neues ADR dokumentiert werden.
