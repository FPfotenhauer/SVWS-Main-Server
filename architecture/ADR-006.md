# 📄 ADR-006

## Logging- & Monitoring-Grundkonzept (MVP – leichtgewichtig)

---

**Status:** Accepted (MVP)
**Datum:** 2026-02-14
**Autor:** Architekturteam Schulträger-Server
**Referenzen:**

* ADR-001 (Hexagonale Architektur)
* ADR-003 (Authentifizierung & JWT)
* ADR-004 (Multi-Tenancy-Strategie)
* ADR-005 (SVWS-Integration MVP)
* arc42 Abschnitt 8 (Querschnittliche Konzepte – Logging, Monitoring)

---

# 1. Kontext

Der Schulträger-Server:

* Verwaltet mehrere Mandanten
* Kommuniziert mit externen SVWS-Servern
* Führt manuelle Synchronisationsprozesse aus
* Ist mandantenfähig
* Hat sicherheitsrelevante Operationen

Für den MVP benötigen wir:

* Nachvollziehbarkeit von Fehlern
* Transparenz bei SVWS-Ausfällen
* Mandantenbezogene Log-Auswertung
* Basis-Monitoring für Betrieb

Ohne:

* Zentrale Observability-Plattform
* Verteiltes Tracing
* Event-Monitoring
* Alerting-Infrastruktur

---

# 2. Ziel des MVP

Sicherstellen, dass:

* Fehler reproduzierbar sind
* Sync-Probleme analysiert werden können
* Mandanten sauber unterscheidbar sind
* Security-relevante Ereignisse sichtbar sind
* Erweiterung später problemlos möglich ist

---

# 3. Entscheidung

Der MVP verwendet:

> Strukturiertes JSON-Logging auf Applikationsebene
> kombiniert mit leichtgewichtigen Health-Checks und Basis-Metriken

Keine externe Monitoring-Plattform im MVP.

---

# 4. Logging-Strategie

## 4.1 Log-Format

Verwendet wird:

* JSON Logging
* Strukturierte Logs
* Keine reinen Textlogs

Quarkus Konfiguration:

```
quarkus.log.console.json=true
```

---

## 4.2 Pflichtfelder in jedem Log

| Feld        | Beschreibung    |
| ----------- | --------------- |
| timestamp   | Zeit            |
| level       | INFO/WARN/ERROR |
| user_id     | JWT sub         |
| request_id  | Korrelations-ID |
| path        | API-Endpunkt    |
| message     | Beschreibung    |
| duration_ms | falls relevant  |

Hinweis: Da Mandanten strikt auf getrennte Datenbanken verteilt sind, existiert kein globaler `tenant_id`-Claim innerhalb der Anwendungsdaten. Logs sollten fallweise kontextspezifische Mandanteninformationen enthalten, wenn diese durch das Deployment verfügbar sind (z. B. als Instanz- oder Deployment-ID), aber `tenant_id` ist kein Pflichtfeld mehr.

---

## 4.3 Request-ID

Bei jedem HTTP-Request:

* Automatisch generierte UUID
* In MDC gespeichert
* In alle Logs des Requests injiziert

Ziel:

* Fehlerverfolgung
* Support-Nachvollziehbarkeit

---

# 5. Log-Level-Strategie

| Level | Verwendung                                     |
| ----- | ---------------------------------------------- |
| INFO  | Business-Aktionen                              |
| WARN  | Externe Probleme (z. B. SVWS nicht erreichbar) |
| ERROR | Systemfehler                                   |
| DEBUG | Nur lokal/dev                                  |

Produktivsystem:

* Standard-Level = INFO

---

# 6. Logging von SVWS-Aufrufen (MVP-spezifisch)

Bei jedem SVWS-Aufruf werden geloggt:
* schule_id
* svws_url
* Dauer
* HTTP-Status
* Ergebnis

Nicht geloggt werden:

* Passwörter
* Access Tokens
* Sensitive Payloads

---

# 7. Sicherheits-Logging

Folgende Ereignisse werden geloggt:

* Login erfolgreich
* Login fehlgeschlagen
* Unauthorized Zugriff
* Rollenverletzung
* Mandantenverletzung (falls implementiert)

Ziel:

* Sicherheitsanalyse
* Forensik im Fehlerfall

---

# 8. Monitoring (MVP-Level)

## 8.1 Health-Endpoints

Quarkus SmallRye Health:

```
/q/health
/q/health/live
/q/health/ready
```

Checks:

* Datenbank erreichbar
* SVWS-Client konfiguriert

---

## 8.2 Basis-Metriken

Quarkus SmallRye Metrics:

Erfasst:

* HTTP-Request Count
* HTTP-Fehlerrate
* SVWS-Aufrufdauer
* Anzahl Synchronisationen

Noch keine externe Prometheus-Integration.

---

# 9. Fehlertransparenz für Admin

UI zeigt:

* Letzter Sync-Zeitpunkt
* Letzter Status
* Letzte Fehlermeldung (bereinigt)
* Erreichbarkeit

Logs bleiben Backend-intern.

---

# 10. Betriebsmodell (MVP)

Deployment:

* Logs gehen auf STDOUT
* Container-Logs werden durch Docker gespeichert
* Optional: Docker Log Rotation

Keine zentrale Log-Aggregation im MVP.

---

# 11. Nicht implementiert im MVP

Bewusst nicht enthalten:

* ❌ ELK Stack
* ❌ Grafana Dashboard
* ❌ Alerting
* ❌ Distributed Tracing
* ❌ OpenTelemetry
* ❌ SIEM Integration

Begründung:

* Overhead zu hoch
* MVP-Fokus
* Geringe Last
* Ein Mandant in Pilotphase

---

# 12. Erweiterungspfad (V2)

Später möglich:

* Prometheus Integration
* Grafana Dashboard
* Alerting bei SVWS-Ausfällen
* Audit-Log-Tabelle
* OpenTelemetry Tracing
* Zentrale Log-Aggregation

---

# 13. Qualitätsbewertung

| Qualitätsziel       | Bewertung |
| ------------------- | --------- |
| Nachvollziehbarkeit | Hoch      |
| Sicherheit          | Hoch      |
| Wartbarkeit         | Hoch      |
| Skalierbarkeit      | Mittel    |
| Betriebsreife       | Mittel    |
| Komplexität         | Niedrig   |

---

# 14. Risiken

| Risiko                | Gegenmaßnahme      |
| --------------------- | ------------------ |
| Log wächst stark      | Log Rotation       |
| Fehlende Alerts       | Manuelle Kontrolle |
| Sensible Daten im Log | Code Review Regel  |

---

# 15. Gültigkeit

Dieses Logging- & Monitoring-Konzept gilt für:

* MVP Phase
* Manuelle Schulverwaltung
* Rolle ADMIN
* Synchrone SVWS-Integration

Erweiterungen erfolgen per neuem ADR.

---

# 🎯 Strategische Wirkung

Mit ADR-006:

* Betrieb ist transparent
* Fehler sind nachvollziehbar
* Mandanten sind im Log sichtbar
* Security ist auditierbar
* Upgrade auf professionelle Observability ist vorbereitet
