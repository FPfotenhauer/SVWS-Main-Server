# 📄 ADR-004

## Multi-Tenancy-Strategie für den Schulträger-Server

---

**Status:** Accepted
**Datum:** 2026-02-14
**Autor:** Architekturteam Schulträger-Server
**Referenzen:**

* ADR-001 (Hexagonale Architektur)
* ADR-002 (Persistenzstrategie)
* arc42 Abschnitt 4 (Lösungsstrategie)
* arc42 Abschnitt 8 (Querschnittliche Konzepte)

---

# 1. Kontext

Der Schulträger-Server verwaltet:

* Einen oder mehrere Schulträger
* Viele Schulen je Schulträger
* Externe SVWS-Server je Schule
* Zukünftig Benutzer, Rollen, Rechte, Logs

Langfristige Anforderungen:

* Möglichkeit, mehrere Schulträger zu betreiben
* Strikte Datenisolation zwischen Mandanten
* Mandantenfähige Rollenmodelle
* Vorbereitung für SaaS-Betrieb
* Erweiterbarkeit ohne Re-Architektur

Es muss entschieden werden:

> Wie wird Mandantenfähigkeit umgesetzt?

---

# 2. Begriffsklärung

**Mandant (Tenant)** = Schulträger

Begründung:

* Schulträger ist die organisatorische Einheit
* Schulen gehören logisch zu einem Schulträger
* Schulträger sind voneinander isoliert
* Deployment kann später SaaS-fähig sein

Schule ist **keine** Mandanteneinheit, sondern eine Domänen-Entität.

---

# 3. Betrachtete Alternativen

## Option A – Separate Datenbank pro Mandant

**Vorteile**

* Maximale Isolation
* Einfache rechtliche Trennung

**Nachteile**

* Hoher Betriebsaufwand
* Migrationen mehrfach
* Monitoring komplex
* Skalierung ineffizient
* Deployment-Overhead

Abgelehnt.

---

## Option B – Schema pro Mandant (PostgreSQL Schema)

**Vorteile**

* Gute Isolation
* Gemeinsame Infrastruktur
* Gute Strukturierung

**Nachteile**

* Komplexe Migrationen
* Flyway schwieriger
* Querying über Mandanten hinweg komplex
* Dev/Test Setup kompliziert

Abgelehnt für V1.

---

## Option C – Gemeinsame Datenbank, Mandanten-ID pro Tabelle

Struktur:

```sql
tenant_id UUID NOT NULL
```

**Vorteile**

* Einfacher Betrieb
* Einfache Migration
* Saubere Erweiterbarkeit
* Gute Performance
* Gut mit Flyway kombinierbar
* SaaS-geeignet
* Gute Integration mit Quarkus

**Nachteile**

* Strikte Disziplin notwendig
* Fehlerhafte Queries können Isolation brechen

✅ **Diese Option wird gewählt.**

---

# 4. Entscheidung

Der Schulträger-Server verwendet:

> Single Database – Shared Schema – Tenant-ID pro Tabelle

---

# 5. Technische Umsetzung

## 5.1 Mandanten-Identifikation

Jeder Request enthält eine `tenant_id`.

Quelle:

* JWT Claim (zukünftig)
* Alternativ HTTP Header (intern)
* Niemals aus Query Parameter

---

## 5.2 Datenbankschema

Beispiel:

```sql
CREATE TABLE schule (
    id UUID PRIMARY KEY,
    tenant_id UUID NOT NULL,
    name VARCHAR(255),
    svws_url VARCHAR(255),
    status VARCHAR(50),
    created_at TIMESTAMP,
    updated_at TIMESTAMP
);
```

Index:

```sql
CREATE INDEX idx_schule_tenant
ON schule(tenant_id);
```

---

## 5.3 Zugriffsschicht

Repositories dürfen niemals ohne Tenant-Filter arbeiten.

Beispiel:

```java
find("tenantId = ?1", tenantId)
```

Zukünftig:

* Hibernate Filter oder Interceptor
* Automatische Tenant-Injection

---

## 5.4 Architektur-Integration

### Domain Layer

* Kennt keine tenant_id

### Application Layer

* Erhält tenant_id aus Security Context
* Übergibt tenant_id an Repository

### Infrastructure Layer

* Implementiert tenant-aware Queries

---

# 6. Isolationsebene

Isolation erfolgt auf:

| Ebene       | Umsetzung                      |
| ----------- | ------------------------------ |
| API         | Security Filter prüft Tenant   |
| Application | Tenant wird explizit übergeben |
| DB          | tenant_id in jeder Tabelle     |
| Index       | Performance-Sicherung          |

---

# 7. Sicherheitsmodell (Vorbereitung für ADR-003)

JWT enthält:

```json
{
  "sub": "user-id",
  "tenant_id": "uuid",
  "roles": ["ADMIN"]
}
```

Security Context extrahiert tenant_id.

---

# 8. Konsequenzen

## Positive

* SaaS-fähig
* Einfache Migration
* Geringer Betriebsaufwand
* Gute Performance
* Gute Erweiterbarkeit
* Mandantenübergreifende Admin-Funktion möglich

## Negative

* Entwicklerdisziplin zwingend
* Gefahr von fehlendem Tenant-Filter
* Testaufwand höher

---

# 9. Qualitätsziele

| Ziel            | Bewertung |
| --------------- | --------- |
| Isolation       | Hoch      |
| Wartbarkeit     | Hoch      |
| Skalierbarkeit  | Hoch      |
| Performance     | Hoch      |
| Sicherheit      | Hoch      |
| Betriebsaufwand | Niedrig   |
| Erweiterbarkeit | Sehr hoch |

---

# 10. Betriebsmodell

* Eine PostgreSQL-Instanz
* Mandanten in gleicher DB
* Backup gesamt
* Restore tenant-spezifisch per Query möglich

---

# 11. Risiken

| Risiko                            | Gegenmaßnahme                        |
| --------------------------------- | ------------------------------------ |
| Entwickler vergisst tenant filter | Code Reviews + Tests                 |
| Security-Fehler                   | Zentrale Tenant-Injection            |
| Performance bei vielen Mandanten  | Indexierung + Partitionierung später |

---

# 12. Zukunftserweiterungen

Möglich:

* PostgreSQL Partitionierung nach tenant_id
* Soft Delete pro Tenant
* Mandanten-Quota
* Mandanten-Statistik

---

# 13. Gültigkeit

Diese Multi-Tenancy-Strategie gilt für:

* Alle Datenbanktabellen
* Alle neuen Module
* Alle zukünftigen Erweiterungen

Abweichungen müssen durch eigenes ADR dokumentiert werden.
